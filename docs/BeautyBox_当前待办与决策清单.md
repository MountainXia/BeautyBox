## 一、已确认事项（锁定继承，不再列入待办）

1. **核心产品体验与本地隐私原则**：「简单为主，精细可选」、纯本地无账号无登录、沙盒私有存储、离线可用、自愿 iCloud 备份、导出/恢复零付费墙（见 [PRD 第 1 节](file:///home/xianggujiang/projects/BeautyBox/docs/BeautyBox_产品需求规格说明书_V3.0.md)）。
2. **TASK02.1 浏览器交互原型冻结**：生命周期交互修复与顶部安全区配色收尾完成，已冻结于 `f6752ac` / 标签 `v0.2-task02.1-frozen`。
3. **M4 美瞳独立一级分类**：美瞳保持独立一级分类，不并入美妆工具或其他。
4. **M6 有效期不猜测与 `min()` 双计算**：未填生产/PAO 禁止按分类猜效期；有生产+保质期且已填开封+PAO 时取 **`min(未开封截止日, 开封日期 + PAO)`**。
5. **M7 妆容四项评分全选填**：整体满意度、妆容协调度、色彩表现、持妆表现均选填，未评分存真 `NULL`，**严禁计为 0 分拉低均分**。
6. **M8 底层多币种最小货币单位存储**：严禁 `Float`、严禁跨币种直接相加、严禁伪汇率换算。

## 二、已收口为「推荐定稿」事项（默认按最佳实践执行，无需逐项开会）

> 如用户在整体审阅中无异议，以下结论将在下一阶段随 `V3-04` / `V3-05` 直接落地，不再额外暂停提问：

1. **M1 名称保护（`is_custom_name`）**：显式布尔列记录自定义状态；建议名为 `品牌 + 最细品类 (+ 色号)` 去重拼接；规格和拥有件数不拼入 `name`。
2. **M2/M9 生命周期四态、独立重置与 `idle` 废弃迁移**：核心态定为 `unrecorded / unopened / in_use / finished`；`idle` 废弃，历史数据迁至 `in_use` 并写备注；`unrecorded` 禁入快捷切换栏，仅详情页独立红色确认重置且保护生产日期、效期原始参数、购买资料、照片及历史妆容日志；任何弹窗取消零部分保存。
3. **M4 美瞳抛期单源机制**：`replacement_cycle_code` 作为日抛/双周抛/月抛/半年抛/年抛唯一事实来源，界面筛选项由此动态生成，彻底避免“分类和属性互相打架”。
4. **M5 规格与数量**：`Product` 存规格（`ml/g/片/支/枚/其他`），拥有数量=未删未用完 `ProductItem` 实时件数；减件优先删空白 `unrecorded` 实物，涉及有日期/价格/妆容关联实例时禁静默盲删。
5. **M6 4 层日期来源与美妆工具豁免**：严格隔离 `raw_input / system_computed / user_confirmed / display_result`；强校验 `opened_date >= manufacture_date`；化妆刷/粉扑等非液体工具标 `expiry_management_mode = 'optional'` 免刺眼效期告警；美瞳外包装 EXP 与开封后抛期独立计算。
6. **M7 整数星级与单值风格场景**：采用 `1～5` 整数星级；`style`/`scene` 采用「单选精选预设 + 手填短文本 + 留空」，多关键词由 `tags` 承载；再次编辑保留既有照片与快照。
7. **M10 混合分层属性模型**：通用高频字段与 `shade` 留主列，美瞳核心光学/周期采用轻量结构，中低频说明性属性入受控版本化 JSON（**严禁建立通用 EAV 表**）。
8. **历史快照与图片引用计数**：`look_product_items` / `routine_*` 一律 `ON DELETE SET NULL` 护快照；仅 `media_assets` 四表引用总计归 0 后才清理物理文件。

## 三、待用户最终拍板清单（压缩至 4 项）

### `UD-01`（M4）：是否核准 V3.1 完整「9 一级 + 45 二级 + 91 三级」产品分类体系及历史映射方案？
1. **问题是什么**：是否将 `ADR-0002` 第 5.4.2 节列出的 9 大一级分类、45 个二级分类、91 个三级具体品类及第 5.4.3 节 24+ 旧版原型分类全量映射表定稿冻结，作为 iOS App 初始内置分类树？
2. **推荐选项**：**核准本版三级分类全表 + 映射表（推荐）**。完整继承旧版 6+24 全部品类并合理拆分遮瑕、定妆、腮红/修容/高光、身体/洗护/美甲/工具，同时通过 `allow_direct_product = 1` 保证美瞳等叶子两步直选。
3. **其他选项**：进一步合并或删减某些三级节点（如将粉底膏/粉底液仅停留在二级），或继续调整某些易混淆品类的默认归属。
4. **对用户体验的影响**：决定“添加产品”时的分类查找清晰度、列表筛选项覆盖度以及是否误把香水浓度/美瞳抛期当分类导致困惑。
5. **对数据库和后续开发的影响**：直接决定 `categories` 种子数据、稳定 `code` 编码及历史 JSON 导入映射逻辑。
6. **是否阻塞 SQLite 设计**：**是（阻塞 `V3-04` 分类种子与迁移脚本，建议最先拍板）**。

### `UD-02`（M10）：美瞳「Product 与 ProductItem」如何归属（不同度数是否拆款）？
1. **问题是什么**：同一款美瞳（同品牌、同花色、同更换周期，如 Olens Scandi 日抛）往往存在左眼 `-2.50`、右眼 `-3.00` 的多盒不同度数库存，应该归在同一款产品下还是按度数拆成不同产品？
2. **推荐选项**：**同款共用 `Product`，左右眼度数与单盒信息挂在 `ProductItem`（推荐）**。列表中看到「Olens Scandi 日抛 · 共 2 盒」，展开后每盒独立显示左右眼度数、剩余片数与 EXP，贴合「简单为主、精细可选」。
3. **其他选项**：按度数拆成独立 `Product`（即左眼款、右眼款各自独立一条产品卡片）。
4. **对用户体验的影响**：选推荐方案避免双目不同度用户录 1 款美瞳建 2 条主档、传 2 次图、清单翻倍碎片化；选拆分方案则每只眼睛不同度都被算作两“款”产品。
5. **对数据库和后续开发的影响**：决定 `left_eye_power`、`right_eye_power`、`lens_power_mode` 建在 `product_items`（推荐）还是建在 `products` / `product_lens_profiles`。
6. **是否阻塞 SQLite 设计**：**是（阻塞 `V3-04` 美瞳结构化列位置确定）**。

### `UD-03`（M3）：删除产品与妆容是否统一启用「7 天本地软删除回收站」？
1. **问题是什么**：用户删除整款产品（含旗下实物）、单瓶或妆容记录时，是先进入「我的 → 回收站」保留 7 天（可按原 UUID 恢复或手动彻删），还是取消回收站改为仅弹二次确认直接删除？
2. **推荐选项**：**统一启用「7 天本地回收站」（推荐，直接呼应 `测试情况.docx` 用户关于删妆容加 7 天回收站的反馈）**。误删可 7 天内无损找回，期满自动清库与无引用图片并严格保住历史妆容快照。
3. **其他选项**：不建设回收站机制，仅靠“归档”与高危二次确认后直接彻底删除（实现略省 1 个回收站页面与过期任务）。
4. **对用户体验的影响**：有回收站显著降低手误删整款高价值产品或多年妆容日记的后悔成本；无回收站界面更轻但误删不可逆。
5. **对数据库和后续开发的影响**：决定 `products`、`product_items`、`looks` 是否启用 `deleted_at` / `trash_expires_at` 双字段、全局查询过滤与 7 天清理调度。
6. **是否阻塞 SQLite 设计**：**是（阻塞 `V3-04` 表字段与删除清理逻辑最终定型）**。

### `UD-04`（M8）：首页「累计购买金额」如何向用户展示？
1. **问题是什么**：在底层绝不跨币种混加与不假算汇率的前提下，首页概览卡片里的历史累计金额区域应该单选展示 1 种主币种，还是直接平铺全部已有币种？
2. **推荐选项**：**首页仅弱化一行展示用户自选的 1 个主展示币种（默认 CNY），其余币种收敛在旁侧“多币种明细”弹窗独立展示（推荐，呼应 `测试情况.docx` 用户关于单币种弱化占位的反馈）**。
3. **其他选项**：首页卡片内直接分行列出所有消费过的币种总和（如 CNY / JPY / USD 同时占两三行）。
4. **对用户体验的影响**：推荐方案让首屏更聚焦在持有与效期预警，同时依然 100% 诚实分币种保留外币消费账本；平铺方案一目了然但首屏信息略重。
5. **对数据库和后续开发的影响**：仅影响 `app_settings` 中 1 个 UI 展示偏好键与首页 ViewModel 拼装逻辑，**数据库底层存储与汇总 SQL 完全相同**。
6. **是否阻塞 SQLite 设计**：**否（可延后至 `V3-07`/`V3-10` 界面开发前确定，不阻塞 `V3-04`）**。

## 四、暂缓与已废弃清单（严格隔离范围）

### 4.1 明确暂缓（`暂缓` — V1 不做）
1. **外链分享后端服务与好友评分**（原 `TASK 16` 架构评估另案处理，V1 只做纯本地白名单图片分享）。

4. **多设备 CloudKit 实时并发同步**（V1 先落实自愿 `.beautyboxbackup` 备份与安全恢复）。
5. **StoreKit 2 免费额度数值与月/年/买断具体定价**（保持配置化，`V3-17` 商业化阶段前最终确认）。

### 4.2 明确废弃（`已废弃` — 禁止沿用）
1. **`product_items.status = 'idle'`（闲置）**：已废弃，迁移期统一转为 `'in_use'` 并在 `lifecycle_note` 保留 `"[迁移保留] 原状态：闲置"`。
2. **`products.cover_asset_id` 冗余列**：已由 `ADR-0001` 第 4.2 节正式废除，以 `product_photos.is_cover = 1` 作为唯一真相源。
3. **原 V2.0“仅 6 大类 24 小类”与“7 张未定数量 KPI 僵化表”口径**：已被 V3.1 三级树与业务驱动建表替代。
4. **“按分类硬猜未开封/开封后保质期”以及“日抛/月抛分类与属性双写”**：已彻底废止。
