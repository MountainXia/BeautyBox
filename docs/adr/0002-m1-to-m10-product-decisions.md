## 一、历史决策继承声明（不可违背基线）

本 ADR 完全继承此前已获用户确认的长期约束与 `ADR-0001` 技术底座，不作任何削弱：
1. 纯本地优先、无注册登录墙、核心功能 100% 离线可用、不建立 `users`/`auth`/`owner_id`/RLS；
2. 本地存储采用 `Swift + SwiftUI`、`SQLite + GRDB`、`MediaStore` 私有沙盒（禁止 Base64 入库）；
3. `Product` 与 `ProductItem` 严格分离；妆容与流程关联具体单件并保留历史快照；
4. 金额采用整数最小货币单位 + `currency_code`，禁止 `Float`；
5. iCloud 默认关闭，V1 仅做用户主动触发的 `.beautyboxbackup` 备份恢复，强制设 `isExcludedFromBackup = true`（需 Mac/Xcode 真机实测）；
6. V1 仅做白名单本地分享图片（默认排除价格、渠道/获得方式、私人备注、肌肤日记），链接分享与好友评分后置；
7. 会员订阅通过 StoreKit 2 实现，过期不得锁定、删除或阻止查看与导出已有数据。

### M1：产品命名规则
- **当前状态**：名称选填及自动组合 `已确认`；独立编辑标记 `推荐待确认`
- **最终推荐方案**：
  1. **产品名称（选填）**：若用户填写，优先使用自定义名称；若留空，按「品牌 + 二级产品类型（无则一级分类）+ 色号/款式」自动组合（仅拼已有非空项，不用多余分隔符，如 `Zelens 粉底液 浮雕白`；如均空则展示 `未命名产品`）。
  2. **主动编辑保护（独立标记 `is_custom_name`）**：在数据模型中记录 `custom_name TEXT NULL`（或同时设 `is_custom_name INTEGER NOT NULL DEFAULT 0`）。只要用户输入或主动修改了名称，视为手动命名；此后修改品牌、分类、色号或规格时**绝不自动覆盖用户名称**；仅当 `custom_name` 为空时随上述字段联动更新 `display_name`。
  3. **品牌与产品名称的关系**：产品名称中可包含或前置品牌以方便列表一眼识别，但品牌（`brand_id` → `brands.name`）仍作独立结构化外键存储，便于按品牌筛选、统计及不破坏历史快照。
- **被否决方案及原因**：
  - 方案：每次修改品牌/色号无条件重算并覆写 `name`。**否决原因**：会毁坏用户手动整理过的个性化昵称（如“白皮救星粉底”）。
- **对数据模型与 UI 影响**：`products` 表保存 `custom_name TEXT NULL`、`is_custom_name INTEGER NOT NULL DEFAULT 0`、`name TEXT NOT NULL`（展示冗余名）；编辑页提供「清空以恢复自动命名」的辅助小操作。
- **需要用户确认**：**【待用户确认】** 确认保留 `is_custom_name` 独立标记并禁止后续自动覆写用户名称。

### M2：产品生命周期与状态定义
- **当前状态**：核心双态独立 `已确认`；旧状态 `idle` 兼容处理 `推荐待确认`
- **最终推荐方案**：
  1. **生命周期状态（4 大核心态）**：
     - `unrecorded`（**未记录**）：尚未录入使用状态的系统默认/异常重置兜底状态。计入「当前拥有数量」，**绝不作为常规快捷选择按钮展示给用户**，仅归入「待记录使用状态」。
     - `unopened`（**未开封**）：确认持有但尚未启用。计入「当前拥有数量」与「未开封」统计。
     - `in_use`（**使用中**）：已启用在用（须有开封日期）。计入「当前拥有数量」与「使用中」统计。
     - `used_up`（**已用完**）：已空瓶退出当前持有，保留完整历史（含 `used_up_date` 与使用时长）。**不计入「当前拥有数量」**。
     - *(兼容保留)*：`idle`（闲置中）、`disposed`（已丢弃）、`transferred`（已转让）作为底层历史兼容字段；建议 V1 新建与快捷操作只面向上述 4 态，若读到历史 `idle` 计入“仍在持有”。
  2. **有效期状态（4 态，完全独立于生命周期）**：
     - `normal`（正常）：未过期且未达用户设定临期阈值（或已确认有效未超期）。
     - `near_expiry`（即将到期）：距离参考/确认到期日在用户设定的 `near_expiry_days` 天以内（含当天至阈值）。
     - `expired`（已过期）：当前日期晚于最终有效到期日（`today > effective_expiry_date`）。
     - `unknown`（无法判断）：缺少足够计算要素且无用户确认到期日（不猜测）。
  3. **展示与排序优先级**：
     - 同一单件可同时呈双标签：如 **`[未开封]` + `[已过期]`**；
     - 详情单件卡片展示顺序：**第 1 位显示生命周期状态**（表明实物当前处于什么使用阶段），**紧随第 2 位以红色/琥珀色高亮展示有效期风险标签**（`已过期` > `即将到期` > `待重新确认` > `有效期待完善`）。
  4. **异常数据兼容**：若外部导入或历史异常数据出现 `status = 'unrecorded'` 却带有 `opened_date`（或 `opened_date < manufacture_date`），绝不静默归类，通过数据校验标为「数据异常」提示人工核对。
- **被否决方案及原因**：
  - 方案：一旦产品过期自动把 `status` 改为 `expired` 替代 `unopened`/`in_use`。**否决原因**：导致用户无法分辨一瓶过期产品究竟是“全新未拆封”还是“已经开瓶用了一半”。
- **对数据模型与 UI 影响**：`product_items.status` 与有效期计算字段完全解耦；UI 层用两组独立徽章样式表达。
- **需要用户确认**：**【待用户确认】** 确认 V1 快捷切换只保留核心 4 态（`idle` 仅作历史兼容），以及双徽章前后顺序（先状态后风险）。

### M3：删除与回收机制
- **当前状态**：历史记录必须保留 `已确认`；7 天回收站细则 `推荐待确认`
- **最终推荐方案**：
  1. **分级删除语义**：
     - **标记已用完**（推荐）：空瓶退出当前拥有，保留全部消费与使用历史；
     - **移除这 1 件**：误录或不再保留该单件，移出当前列表；
     - **删除整款产品**：整款产品及其未彻底删除单件统一进入 **7 天回收站**（设 `deleted_at` 与 `purge_at`），不立即物理抹除。
  2. **恢复与彻底删除安全**：
     - 在「我的 → 最近删除」统一展示产品与妆容回收项（显示剩余保留天数）；
     - 恢复产品时**严格按原 `UUID` 还原**，即使存在同品牌同分类同色号的新建产品，**绝不合并或覆盖**；
     - 支持二次确认提前彻底删除及到期自动清理；彻底删除时，对关联的 `look_product_items`、`routine_step_products`、`routine_log_items`、`product_usage_logs` 采用 **快照保留 + 外键置空/解绑策略（`ON DELETE SET NULL` 或历史标记保留）**，绝不连带删毁历史妆容、日常打卡或照片；
     - 物理图片文件仅在全库所有表（含历史妆容、日记、持妆）引用计数归 `0` 时方允许由 `MediaStore` 清理。
- **被否决方案及原因**：
  - 方案：删除产品时 `CASCADE` 级联删除关联的妆容使用条目或整篇妆容。**否决原因**：违背“历史妆容可追溯”核心准则。
- **需要用户确认**：**【待用户确认】** 是否确认采用 **7 天回收站（含一键恢复 + 二次确认彻底删除）** 方案。

### M4：产品分类体系（重点重构 · 纳入美瞳独立一级分类）
- **当前状态**：分类原则 `已确认`；**9 大一级分类及完整二级分类方案 `推荐待确认`（需用户最终审阅后才可写入 SQLite 分类字典）**
- **设计理由与调整对比**：
  - 原型 C2 阶段临时使用了 6 个一级分类（`底妆 / 唇妆 / 眼妆 / 腮红修容 / 眉妆 / 护肤`）与 24 个二级分类。随着品类的完整规划，原 6 大类将“彩妆”切得过碎，无法容纳香水、身体、洗护、美甲、美妆工具及**美瞳**。
  - 因此推荐重构为 **9 个平衡、稳定的一级分类**，其中 **「美瞳」作为独立一级分类**，不归入“美妆工具”或“其他”。

#### M4-3：容易混淆的分类归属规则（防止品牌/包装干扰分类）
1. **包装形态不得决定分类**：例如「气垫粉底」和「管装粉底液」均归 `彩妆 → 底妆`；「铁盒固体唇膏/香膏」按功能分入 `唇部产品` 或 `香膏`。
2. **护肤 vs 彩妆跨界（素颜霜/有色防晒/防晒隔离）**：以**主要功效与使用步骤**划分——物理/化学高倍防护归 `护肤 → 防晒`；主打遮瑕润色修饰肤色归 `彩妆 → 底妆`；既有防晒值又有润色隔离以用户场景选归一侧即可，不建交叉重复子分类。
3. **面部工具 vs 美甲工具**：`美甲工具` 归属 `美甲护理` 之下（如光疗灯、甲挫）；`化妆刷、粉扑、睫毛夹、修眉刀` 归属 `美妆工具`；`洁面仪/蒸脸仪` 等归属 `护肤 → 其他护肤` 或 `美妆工具 → 其他化妆工具`。
4. **美瞳隐形眼镜护理液**：若后续用户收纳护理液，可放入 `美瞳 → 其他周期` 或待需时扩展，但当前不强设二级冗余类。

#### M4-4：美瞳分类与更换周期的双轨协同设计
- **推荐规则**：
  1. **二级分类负责浏览与列表筛选**（`日抛 / 月抛 / 半年抛 / 年抛 / 其他周期`），让用户 1 秒看懂与筛选；
  2. **美瞳结构化属性同时保存结构化更换周期字段**（如 `replacement_cycle_code`: `daily` / `monthly` / `half_year` / `yearly` / `biweekly` / `quarterly` / `custom`，及可选 `replacement_days`）；
  3. **一致性校验与联动**：新建美瞳产品选择二级分类（如“月抛”）时自动同步填入 `replacement_cycle_code = 'monthly'`，若选“其他周期”则放开选择双周抛/季抛或自定义天数，**避免用户手填两遍产生矛盾**。
- **需要用户确认**：**【待用户确认】** 确认以上 **9 个一级分类与 47 个二级分类体系（上表含彩妆10、护肤8、香氛4、身体5、头发5、美甲4、工具5、美瞳5、其他1，共47个推荐条目，不擅自锁死可删减合并）** 及原型 6 大类往新 9 大类升级时“将旧 5 个彩妆类自动迁移归入‘彩妆’下的二级分类”之规则。

### M6：生产日期、购买日期、开封日期和有效期
- **当前状态**：基础推算与顺序防呆 `已确认`；美瞳双日期分离规则 `推荐待确认`
- **明确边界**：
  1. **未开封有效期**：仅当 `manufacture_date` 与 `unopened_shelf_months` 均存在时计算；缺项不推算；
  2. **开封后有效期**：仅当 `opened_date` 与 `pao_months` 均存在时计算；缺项不推算；
  3. **用户确认到期日**：永远具有最高展示优先级；不会被自动推算覆写；当依据输入变化时，置 `expiry_needs_reconfirm = true` 提示核对；
  4. **日期修改与状态切换**：
     - 切换为 `未开封` 时清空开封日期并重算未开封到期日；
     - 历史日期修改后立即重算对应推算列并检查 `opened_date >= manufacture_date`、`used_up_date >= opened_date` 且 `>= manufacture_date`；
  5. **美瞳产品的包装有效期 vs 更换周期（重点区分）**：
     - 美瞳盒/瓶身印制的 **包装有效期（EXP）** 属于未开封贮存寿命（可通过「未开封保质期推算」或直接填写「用户确认到期日」记录，缺生产日期时不猜测）；
     - **日抛 / 月抛 / 半年抛 / 年抛更换周期** 是「单副拆封佩戴寿命」，与未开封保质期是两码事，**系统不得仅凭“月抛”就擅自覆盖包装 EXP，也不得把所有商品在缺依据时推算到期日**；拆封日 + 更换周期天数可作为“建议停戴提醒参考”（仅在有效期内取两者更早约束的辅助提示，缺开封日或具体天数时显示「无法判断 / 请核对说明」）。
- **需要用户确认**：**【待用户确认】** 确认美瞳包装有效期与拆封更换周期分离展示、互不猜测推断的规则。

#### M9-1：记录完整性重新定义（按状态与类别区分）
| 维度 | 必须填写 | 有数据时参与计算 | 可选 / 允许缺失（不影响生命周期记录完成） |

| `unopened` | `used_up` | **允许** | 是（二次确认弹窗） | 必填 `used_up_date` (`>= manufacture_date`) | `status='used_up'`, `remaining_percent=0`, 写入 `used_up_date` |
| `in_use` | `unopened` | **允许** | 是（二次确认弹窗） | 无 | **清除 `opened_date` 与 `used_up_date`，`remaining_percent` 强制重置为 `100`**，按未开封规则重算有效期（原型现状连带清除 `confirmed_expiry_date`，**【待确认是否改为仅清基于开封的确认】**） |
| `in_use` | `used_up` | **允许** | 是（二次确认弹窗+时长预览） | 必填 `used_up_date` (`>= opened_date` 且 `>= manufacture_date`) | `status='used_up'`, `remaining_percent=0`, 写入 `used_up_date` |
| `used_up` | `in_use` | **允许** | 是（二次确认弹窗） | **必填 `remaining_percent` (`1..100`) 与 `opened_date` (`>= manufacture_date`)** | `status='in_use'`, `used_up_date=NULL`（若无 PAO 与确认日，状态有效但入有效期待完善 · `缺 PAO`） |
| `used_up` | `unopened` | **不允许** | — | — | 快捷按钮不可用态，点击明确提示原因：「已用完产品不能直接改为未开封，请先恢复为使用中。」 |
| `unopened / in_use / used_up` | **`unrecorded`**（专用重置入口） | **推荐通过产品详情“重置使用状态”入口有条件允许（普通快捷栏仍禁选）** | **必须强二次确认（逐项告知清除范围）** | 无 | **【推荐待确认 · M9-4】** **严格保留**：产品主档（名称、品牌、分类、规格、专属属性、图片、基础备注）、购买记录（价格、币种、购买日期、获得方式）、历史妆容快照及已有使用日志（不得物理删毁）。**仅清除生命周期维度**：`status='unrecorded'`、`opened_date=NULL`、`used_up_date=NULL`、`remaining_percent=100`、`confirmed_expiry_date=NULL`、`expiry_confirmed_at=NULL`、`expiry_needs_reconfirm=0`、`opened_computed_expiry=NULL`；生产日期与未开封保质期/PAO 可作为产品包装固有信息默认保留（或让用户勾选是否同清） |

#### M9-3：美瞳专属生命周期补充规则（**`推荐待确认`**）
1. **包装 EXP 与拆封周期分离**：日抛（1天）/月抛（30天或1月）/半年抛（6月）/年抛（12月）属于**开封佩戴寿命**，不能代替未开封保质期；
2. **禁止盲目推断**：缺少生产日期与未开封保质期（且未手动确认 EXP）时，不推断盒身包装有效期；开封后缺少具体更换周期天数/选择“其他周期”未填时，提示「无法判断 / 请核对产品说明」；
3. **日抛特殊提醒（建议）**：当用户将「日抛」美瞳拆封（使用中）时，提示单副当日佩戴建议，不影响整盒剩余未拆封副数（多件模型下建议 1 件对应 1 副或 1 盒并在数量单位明确）。

- **需要用户确认（M9）**：
  1. **【待用户确认】** 是否采用「详情页专用二次确认入口重置为 `unrecorded`（严格保留主档、购买信息、历史妆容与使用日志，仅清生命周期状态/开封/用完/剩余比例/确认到期日，保留生产日期与保质期参数）」；
  2. **【待用户确认】** 「使用中 → 未开封」时原手动 `confirmed_expiry_date` 的处理方式（全清空重算 vs 仅提示重确认）；
  3. **【待用户确认】** 美瞳生命周期上述 3 条边界及已过期未开封点击开封时是否弹出强警告。

#### M10-3：三种数据存储结构深度对比评估

| 评估维度 | 方案 A：全表共用通用单张扁平表（把各分类专属列全加在 `products` 上） | 方案 B：通用字段 + 分类专属 JSON 列（`products.specialty_attrs_json` / `items.item_attrs_json`） | 方案 C：通用字段 + 分类专属结构化表 / 模型（核心高频列落正式表 + 美瞳等强参数建专门结构化扩展表或强类型 Swift 模型映射） |
|---|---|---|---|
| **开发复杂度** | 低（单表 CRUD，无 JOIN） | 低～中（少改表结构，靠 Codable 编解码 JSON） | 中（仅对真正有独立字段群的类如 `美瞳` 建扩展表 `contact_lens_specs` 或 `product_item_lens_powers`，其余轻量字段可与 `products` 或 JSON 共存） |
| **查询效率** | 高（全单表索引） | 中（按分类专属属性查询需 `json_extract`） | 高（可对左右眼度数、周期、色号直接建列索引） |
| **数据完整性与 CHECK** | 差（大量无关字段满表为 `NULL`，易误用） | 中（SQLite 层无法对 JSON 内部属性加 `CHECK` 约束） | **优**（结构化字段可直接做非负/范围 `CHECK` 与 Swift 强类型约束） |
| **后续扩展性** | 差（每加 1 个品类属性就须迁移加列） | **极佳**（新加护肤功效或香型只需更新 Swift Codable） | **良好**（高频强结构表稳定 + 低频扩展属性不污染主表） |
| **SQLite 适配性与迁移** | 简单但主表会逐步臃肿 | 极易迁移（无需加列 Migration） | 清晰可控，通过 GRDB 外键 `1:1`（`product_id` PK/FK）或 `product_item_id` 关联极易维护 |
| **Swift 类型安全** | 一般（大量可选值散落主模型） | 高（解包为枚举关联 `enum CategorySpecialtyDetails`） | **极高**（主模型与 `ContactLensProfile` / `FragranceProfile` 完全强类型） |

- **V1 推荐方案（混合务实版，归于方案 C 体系 · `推荐待确认`）**：
  - **推荐结构**：
    1. **最高频公共属性**直接作为简洁可空列保留在 `products`（`shade`、`texture`、`finish`、`expiry_tracking_enabled`）；
    2. **美瞳因存在「左右眼不同度数 + 同款多件买不同度数 + BC/DIA/周期/包装」强结构需求**，单独建立强类型结构化字段（如 `product_item` 维度存储单件左/右眼度数，与主档层面存储 `replacement_cycle_code`、BC/DIA/含水量/花纹）；
    3. **香水浓度/香调、护肤肤质/功效等中等低频文字属性**，采用方案 B 的轻量受控 JSON（`specialty_attrs_json` + Swift 强类型 `Codable` 结构枚举解码），既避免 30 多个稀疏空列污染 `products` 主表，也无需建设复杂的通用 EAV（实体-属性-值）系统，保留未来平滑拆表空间。
- **需要用户确认**：**【待用户确认】** 确认 V1 采用上述「通用主表 + 美瞳强结构度数/周期 + 其余品类受控 JSON 结构模型」（或纯方案 B / 纯方案 C）。

## 三、跨决策冲突检查结果

| 检查组合 | 检查结果与修正说明 |
|---|---|
| **M2 × M9** | 一致：4 态生命周期与 4 态有效期完全正交；`unrecorded` 禁入快捷切换、仅作为新建兜底或专用重置入口；`expired + unopened` 允许并存。 |
| **M4 × M10** | 一致：禁止把香水浓度、香调、色号、美瞳度数/BC/DIA 当作分类；`M4` 决定“属于哪一类”，`M10` 决定“展示和记录哪些专属属性”。美瞳二级分类与 M10 `replacement_cycle_code` 双向同步，不重复维护冲突。 |
| **M5 × M9** | 一致：规格与数量单位严格分离；`used_up` 退出持有数、`unopened` 强制重置 `remaining_percent=100%`。 |
| **M6 × M9** | 一致：无生产日期或无 PAO 时绝不瞎猜；美瞳的**盒身包装有效期（EXP）**归 M6 未开封/确认到期管理，**日抛/月抛/半年抛/年抛**归 M9/M10 佩戴更换周期，互不覆盖。 |
| **M7 × M10** | 无冲突：妆容关联 `ProductItem` 并存快照，不依赖品类专属属性表即可正常追溯产品名/品牌/色号/分类；若美瞳入妆容，同样可被关联引用。 |
| **M3 × 历史记录保留** | 一致：7 天回收站恢复按 UUID 独立还原；彻底删除对妆容/日常使用记录均执行外键 `SET NULL` + 快照保留；物理图片仅在引用数为 `0` 时清除。 |
| **美瞳分类 × 美瞳生命周期 × 美瞳属性** | 特别澄清：**多盒/多副不同度数的同款美瞳**共用同一 `Product`（花纹/直径/基弧/周期），不同度数（左/右眼）分别记录在各自 `ProductItem` 上，彻底消除“同款不同度数要建好几个重复产品”的冗余痛点。 |
